# Feature Specification: 소셜 피드 (Social Feed)

**Feature Branch**: `001-social-feed`
**Created**: 2025-11-09
**Status**: Draft

## 개요 (Overview)

CrossFeed는 인스타그램의 UX를 벤치마킹한 소셜 피드 애플리케이션입니다. 사용자는 이미지를 공유하고, 댓글을 통해 소통하며, 푸시 알림을 통해 실시간 피드백을 받습니다. Phase 1에서는 피드 기능에 집중하며, Phase 2에서 채팅 기능을 추가할 예정입니다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 이미지 포스트 생성 및 공유 (Priority: P1)

사용자가 이미지를 선택하고 캡션을 작성하여 피드에 게시합니다. 이는 CrossFeed의 핵심 가치인 콘텐츠 생성의 기반이 됩니다.

**Why this priority**: 콘텐츠가 없으면 피드가 존재할 수 없습니다. 포스트 생성은 모든 소셜 기능의 전제조건이며, 이 기능만으로도 사용자가 자신의 콘텐츠를 저장하고 공유할 수 있는 기본적인 가치를 제공합니다.

**Independent Test**: 사용자가 이미지를 업로드하고 캡션을 입력한 후 "게시" 버튼을 클릭하면, 포스트가 성공적으로 생성되고 데이터베이스에 저장되는지 확인할 수 있습니다. 피드 화면 없이도 API나 데이터베이스를 직접 확인하여 테스트 가능합니다.

**Acceptance Scenarios**:

1. **Given** 사용자가 로그인되어 있고, **When** 이미지를 선택하고 캡션을 입력한 후 "게시"를 클릭하면, **Then** 포스트가 생성되고 성공 메시지가 표시됩니다
2. **Given** 사용자가 포스트 생성 화면에 있고, **When** 이미지를 선택하지 않고 "게시"를 클릭하면, **Then** "이미지를 선택해주세요" 오류 메시지가 표시됩니다
3. **Given** 사용자가 이미지를 선택했고, **When** 캡션 없이 "게시"를 클릭하면, **Then** 포스트가 생성됩니다 (캡션은 선택사항)
4. **Given** 사용자가 큰 용량의 이미지를 선택했고, **When** "게시"를 클릭하면, **Then** 업로드 진행 상태가 표시되고 완료 후 포스트가 생성됩니다

---

### User Story 2 - 피드 조회 (Priority: P2)

사용자가 피드 화면에서 다른 사용자들이 게시한 이미지 포스트들을 시간순으로 조회합니다.

**Why this priority**: 콘텐츠 소비는 소셜 앱의 핵심입니다. 사용자들이 다른 사람들의 콘텐츠를 볼 수 없다면 앱을 사용할 이유가 없습니다. 포스트 생성 다음으로 중요한 기능이며, 이 둘만으로도 기본적인 소셜 피드 앱이 완성됩니다.

**Independent Test**: 여러 포스트를 사전에 생성해두고, 사용자가 피드 화면을 열었을 때 모든 포스트가 최신순으로 표시되는지 확인할 수 있습니다. 무한 스크롤이나 페이지네이션도 독립적으로 테스트 가능합니다.

**Acceptance Scenarios**:

1. **Given** 피드에 여러 포스트가 존재하고, **When** 사용자가 피드 화면을 열면, **Then** 최신 포스트부터 시간순으로 표시됩니다
2. **Given** 사용자가 피드 화면에서 스크롤하고, **When** 화면 하단에 도달하면, **Then** 다음 배치의 포스트들이 자동으로 로드됩니다
3. **Given** 피드에 포스트가 없고, **When** 사용자가 피드 화면을 열면, **Then** "아직 게시된 포스트가 없습니다" 메시지가 표시됩니다
4. **Given** 사용자가 피드를 보고 있고, **When** 새로운 포스트가 게시되면, **Then** 피드 상단에 "새 포스트 보기" 버튼이 나타나고 클릭 시 새로고침됩니다
5. **Given** 각 포스트에, **When** 사용자가 피드를 조회하면, **Then** 이미지, 작성자 정보, 캡션, 작성 시간, 댓글 수가 표시됩니다

---

### User Story 3 - 댓글 작성 및 조회 (Priority: P3)

사용자가 포스트에 댓글을 작성하고, 다른 사용자들의 댓글을 조회하여 소통합니다.

**Why this priority**: 댓글은 사용자 간 상호작용의 핵심입니다. 포스트 생성과 조회만으로도 기본적인 피드는 동작하지만, 댓글이 있어야 진정한 소셜 경험이 완성됩니다. 이 기능은 앞의 두 기능과 독립적으로 개발 및 테스트가 가능합니다.

**Independent Test**: 특정 포스트에 대해 댓글을 작성하고, 해당 포스트의 댓글 목록을 조회하여 방금 작성한 댓글이 표시되는지 확인할 수 있습니다. 댓글 수정 및 삭제도 독립적으로 테스트 가능합니다.

**Acceptance Scenarios**:

1. **Given** 사용자가 포스트를 보고 있고, **When** 댓글 입력란에 텍스트를 입력하고 "게시"를 클릭하면, **Then** 댓글이 추가되고 댓글 목록에 즉시 표시됩니다
2. **Given** 포스트에 여러 댓글이 있고, **When** 사용자가 포스트를 열면, **Then** 모든 댓글이 작성 시간순으로 표시됩니다
3. **Given** 사용자가 자신의 댓글을 보고 있고, **When** 삭제 버튼을 클릭하고 확인하면, **Then** 댓글이 삭제되고 목록에서 제거됩니다
4. **Given** 사용자가 빈 댓글을 작성하려 하고, **When** "게시"를 클릭하면, **Then** "댓글 내용을 입력해주세요" 오류 메시지가 표시됩니다
5. **Given** 포스트에 댓글이 없고, **When** 사용자가 포스트를 열면, **Then** "첫 번째 댓글을 남겨보세요" 메시지가 표시됩니다

---

### User Story 4 - 푸시 알림 수신 (Priority: P4)

사용자는 자신의 포스트에 댓글이 달리거나 다른 상호작용이 발생하면 푸시 알림을 받습니다.

**Why this priority**: 푸시 알림은 사용자 참여와 재방문을 유도하는 핵심 기능입니다. 앞의 세 기능만으로도 기본적인 소셜 피드는 동작하지만, 알림이 있어야 사용자들이 앱으로 다시 돌아오게 됩니다. 독립적으로 구현하고 테스트할 수 있습니다.

**Independent Test**: 한 사용자가 다른 사용자의 포스트에 댓글을 작성하면, 포스트 작성자에게 푸시 알림이 전송되는지 확인할 수 있습니다. 알림 설정 및 권한 관리도 독립적으로 테스트 가능합니다.

**Acceptance Scenarios**:

1. **Given** 사용자 A가 알림을 허용했고 사용자 B가 A의 포스트에 댓글을 작성하면, **When** 댓글이 게시되면, **Then** 사용자 A에게 "B님이 회원님의 게시물에 댓글을 남겼습니다" 푸시 알림이 전송됩니다
2. **Given** 사용자가 앱을 사용 중이고, **When** 새 알림이 발생하면, **Then** 인앱 알림 배너가 표시됩니다
3. **Given** 사용자가 푸시 알림을 받고, **When** 알림을 탭하면, **Then** 앱이 열리고 해당 포스트 상세 화면으로 이동합니다
4. **Given** 사용자가 알림 설정에서, **When** 댓글 알림을 비활성화하면, **Then** 이후 댓글에 대한 푸시 알림을 받지 않습니다
5. **Given** 사용자가 앱을 사용하지 않는 상태에서, **When** 알림을 받으면, **Then** 기기의 알림 센터에 표시됩니다

---

### Edge Cases

- 사용자가 지원하지 않는 이미지 포맷(예: TIFF, BMP)을 업로드하려고 하면 어떻게 되나요?
- 매우 긴 캡션(예: 10,000자 이상)을 입력하면 시스템은 어떻게 처리하나요?
- 네트워크 연결이 불안정한 상태에서 포스트를 업로드하려고 하면 어떻게 되나요?
- 사용자가 동일한 이미지로 여러 번 빠르게 포스트를 생성하려고 하면 중복 생성을 방지하나요?
- 댓글에 욕설이나 부적절한 콘텐츠가 포함되어 있으면 어떻게 처리하나요?
- 삭제된 포스트의 댓글은 어떻게 되나요?
- 사용자가 알림 권한을 거부했다가 나중에 허용하면 이전 알림도 받을 수 있나요?
- 웹 브라우저에서 푸시 알림을 지원하지 않는 경우 어떻게 처리하나요?
- 무한 스크롤 중에 새로운 포스트가 추가되면 스크롤 위치가 유지되나요?

## Requirements *(mandatory)*

### Functional Requirements

**인증 및 사용자 관리**

- **FR-001**: 시스템은 사용자가 이메일과 비밀번호로 회원가입할 수 있어야 합니다
- **FR-002**: 시스템은 사용자가 이메일과 비밀번호로 로그인할 수 있어야 합니다
- **FR-003**: 시스템은 각 사용자에게 고유한 사용자명(username)을 할당해야 합니다
- **FR-004**: 시스템은 사용자 프로필 정보(이름, 프로필 사진, 자기소개)를 저장해야 합니다

**포스트 생성 및 관리**

- **FR-005**: 사용자는 이미지 파일을 선택하여 포스트를 생성할 수 있어야 합니다
- **FR-006**: 시스템은 JPEG, PNG, WebP 이미지 포맷을 지원해야 합니다
- **FR-007**: 시스템은 이미지 파일 크기를 최대 10MB로 제한해야 합니다
- **FR-008**: 사용자는 포스트에 선택적으로 캡션(최대 2,000자)을 추가할 수 있어야 합니다
- **FR-009**: 시스템은 포스트 생성 시 작성자, 이미지 URL, 캡션, 생성 시간을 저장해야 합니다
- **FR-010**: 사용자는 자신의 포스트를 삭제할 수 있어야 합니다
- **FR-011**: 포스트 삭제 시 관련된 모든 댓글도 함께 삭제되어야 합니다

**피드 조회**

- **FR-012**: 시스템은 모든 사용자의 포스트를 최신순으로 정렬하여 피드에 표시해야 합니다
- **FR-013**: 피드는 무한 스크롤 방식으로 구현되어야 하며, 한 번에 20개의 포스트를 로드해야 합니다
- **FR-014**: 각 포스트에는 이미지, 작성자 프로필 사진, 작성자 이름, 캡션, 작성 시간, 댓글 수가 표시되어야 합니다
- **FR-015**: 사용자는 피드를 아래로 당겨서 새로고침(pull-to-refresh)할 수 있어야 합니다

**댓글**

- **FR-016**: 사용자는 포스트에 댓글을 작성할 수 있어야 합니다
- **FR-017**: 댓글은 최대 500자로 제한되어야 합니다
- **FR-018**: 시스템은 댓글 작성 시 작성자, 포스트 ID, 댓글 내용, 생성 시간을 저장해야 합니다
- **FR-019**: 댓글은 작성 시간순으로 정렬되어 표시되어야 합니다
- **FR-020**: 사용자는 자신의 댓글을 삭제할 수 있어야 합니다
- **FR-021**: 포스트 작성자는 자신의 포스트에 달린 모든 댓글을 삭제할 수 있어야 합니다

**푸시 알림**

- **FR-022**: 시스템은 사용자의 포스트에 댓글이 달리면 해당 사용자에게 푸시 알림을 전송해야 합니다
- **FR-023**: 사용자는 알림 수신 여부를 설정할 수 있어야 합니다
- **FR-024**: 푸시 알림 클릭 시 해당 포스트 상세 화면으로 이동해야 합니다
- **FR-025**: 시스템은 웹과 모바일 모두에서 푸시 알림을 지원해야 합니다

**크로스 플랫폼**

- **FR-026**: 시스템은 웹 브라우저와 모바일 앱(WebView)에서 동일한 기능과 UI를 제공해야 합니다
- **FR-027**: 모바일 앱은 기기의 카메라와 갤러리에 접근하여 이미지를 선택할 수 있어야 합니다
- **FR-028**: 시스템은 다양한 화면 크기(모바일, 태블릿, 데스크톱)에 반응형으로 대응해야 합니다

### Key Entities

- **User (사용자)**:
  - 고유 ID, 이메일, 비밀번호(암호화), 사용자명(고유), 이름, 프로필 사진 URL, 자기소개, 생성일시
  - 여러 포스트와 댓글을 작성할 수 있음

- **Post (포스트)**:
  - 고유 ID, 작성자 ID(User 참조), 이미지 URL, 캡션(선택), 생성일시
  - 한 명의 사용자(작성자)와 연결되며, 여러 댓글을 가질 수 있음

- **Comment (댓글)**:
  - 고유 ID, 작성자 ID(User 참조), 포스트 ID(Post 참조), 댓글 내용, 생성일시
  - 한 명의 사용자(작성자)와 하나의 포스트에 연결됨

- **Notification (알림)**:
  - 고유 ID, 수신자 ID(User 참조), 알림 유형(댓글), 관련 포스트 ID, 관련 사용자 ID(작성자), 읽음 여부, 생성일시
  - 특정 사용자에게 전송되며, 관련 포스트와 작성자 정보를 포함함

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 이미지 선택부터 포스트 게시까지 30초 이내에 완료할 수 있습니다
- **SC-002**: 피드는 20개의 포스트를 2초 이내에 로드하여 표시합니다
- **SC-003**: 댓글 작성 후 1초 이내에 화면에 반영되고 다른 사용자에게도 표시됩니다
- **SC-004**: 푸시 알림은 이벤트 발생 후 5초 이내에 사용자에게 전송됩니다
- **SC-005**: 시스템은 동시에 1,000명의 사용자가 피드를 조회해도 응답 시간이 3초를 초과하지 않습니다
- **SC-006**: 이미지 업로드 성공률이 95% 이상이어야 합니다 (네트워크 오류 제외)
- **SC-007**: 웹과 모바일 앱에서 동일한 기능이 100% 동일하게 동작해야 합니다
- **SC-008**: 90% 이상의 사용자가 앱 설치 후 첫 포스트를 5분 이내에 생성합니다
- **SC-009**: 알림을 받은 사용자의 70% 이상이 24시간 이내에 앱으로 돌아옵니다

## Assumptions & Constraints

### Assumptions

- 모든 포스트는 기본적으로 공개되며, Phase 1에서는 비공개 설정을 지원하지 않습니다
- Phase 1에서는 "팔로우" 기능 없이 모든 사용자의 포스트가 통합 피드에 표시됩니다
- Phase 1에서는 "좋아요" 기능을 제공하지 않으며, Phase 2에서 추가할 예정입니다
- 사용자는 이미지 업로드 시 해당 이미지에 대한 권리를 가지고 있다고 가정합니다
- 댓글은 텍스트만 지원하며, 이미지나 이모티콘은 Phase 2에서 검토됩니다
- 사용자는 안정적인 인터넷 연결을 가지고 있다고 가정합니다 (오프라인 모드는 Phase 2 이후 검토)

### Constraints

- Phase 1에서는 채팅 기능을 제공하지 않으며, UI에 "커밍 순(Coming Soon)" 표시만 합니다
- 이미지 편집 기능(필터, 크롭 등)은 Phase 1 범위를 벗어나며, 사용자는 업로드 전에 외부 앱에서 편집해야 합니다
- 동영상 업로드는 Phase 1에서 지원하지 않습니다
- 콘텐츠 신고 및 모더레이션 기능은 Phase 1 범위를 벗어나며, Phase 2에서 추가됩니다
- 다국어 지원은 Phase 1에서 제공하지 않으며, 한국어만 지원합니다

### 구현 전략

- 4개의 User Story는 하나의 feature 내에서 우선순위 순서대로 점진적으로 구현됩니다 (P1→P2→P3→P4)
- 각 User Story는 독립적으로 개발, 테스트, 배포 가능하도록 설계되었습니다
- 최소 MVP는 US1(포스트 생성) + US2(피드 조회)로 구성되며, US3(댓글) + US4(알림)는 이후 단계에서 추가할 수 있습니다

## Phase 2 Preview

Phase 2에서는 다음 기능들이 추가될 예정입니다:

- **DM/채팅**: 사용자 간 1:1 메시지 및 그룹 채팅
- **팔로우/팔로워**: 사용자 간 팔로우 관계 및 개인화된 피드
- **좋아요**: 포스트에 좋아요 표시
- **콘텐츠 모더레이션**: 신고 기능 및 부적절한 콘텐츠 관리
- **프로필 편집**: 사용자 정보 및 설정 변경
- **검색**: 사용자 및 해시태그 검색

Phase 1 개발 시 이러한 기능들의 확장성을 고려하여 데이터 구조와 아키텍처를 설계해야 합니다.
